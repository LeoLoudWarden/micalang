# AI 辅助开发说明

这个项目从前期设计讨论到代码实现、测试、安全审查、文档起草，全程使用了 AI 辅助。本文说明实际的使用方式：用了什么、怎么分工、怎么验证。原始对话记录见[开发对话选编](conversation.zh-CN.md)。

## 用了什么

| 环节 | AI 承担的角色 | 工具与模型 |
|---|---|---|
| 立项前的设计讨论 | 评估"接管 CPython IO"的可行性，比较 Starlark、gVisor、microVM、WASM 等方案 | 自有 chat 应用, 记录丢失 |
| 引擎开发 | 读需求、起草方案、实现编译器/引擎/VFS/FFI、编写测试与阶段日志 | kimi-code, K3 |
| 安全审查 | 独立子 agent 做对抗性分析；另一个 AI 提供独立安全意见 | kimi-code 子agent, K3；自有 chat 应用, deepseek V4.1f|
| 文档检验 | 让未参与写作的子 agent 盲读设计文档并复述理解，检验是否被误导 | kimi-code 子agent, K3 |
| demo 实测 | 作为**被测对象**：在 Mica VM 里读文档、写代码、发请求的 LLM | OpenAI 兼容 API, qwen3.8 等多种参数量在几十B的开源模型 |

注意 demo 实测与前四行的区别：demo 里的模型不是开发工具，而是实验对象。它检验的是"模型能否仅凭一份语言速览就写出可运行的 Mica 代码"，与引擎本身的质量无关。

## 怎么分工

基本原则：**阶段目标与设计理念由作者定，方案与实现由 AI 起草，采纳与否由作者判断。**

作者做的事：

- 提出并守住设计理念。AI 多次出现理解偏差——想复用早期的 mock_fs 玩具、想把 LLM request 内建进引擎、把 Mica 理解成"给 LLM 用的工具"——都由作者纠正。虚拟化理念、"给 AI 的工具"与"语言引擎"的层次划分、能力靠授予而非内建，这些关键概念均来自作者。
- 把模糊想法转成阶段目标。例如第二阶段的方向不是 AI 建议的"加指令流 + 加资源治理"两个并列任务，而是作者指出它们本质是同一件事：让引擎"真"起来。
- 要求先写方案再动手，对 AI 的"已完成"汇报继续追问，并决定下一阶段做什么。
- 对审查意见做取舍。外部安全审查的三分类（采纳 / 牛角尖 / 合理但暂不补）由作者定调。
- 亲自实测。demo 的 mock 与真实 API 运行之外，作者自己多跑了几次，发现了 AI 未触发的 `IfExp` 编译期崩溃。
- 文档定稿。本项目所有说明性文档的规则是：AI 可以起草，入库前必须经作者人工打磨。

AI 做的事：

- 起草设计草案（指令集、异常表、FFI 边界等）并实现代码与测试。
- 自查、汇报测试计数与遗留问题，提出下一阶段建议。
- 起草文档：阶段日志、语言速览、设计说明（当时的"白皮书"）。
- 提供不同的审查视角。第五阶段的子 agent 对抗性审查确实发现了作者自查未覆盖的问题（如逐语句快照造成的 CPU 放大）。

被否掉的 AI 产出（不完全列举）：

- 把早期讲解用的 mock_fs 当作实现资产复用；
- 把 LLM request / HTTP 等具体能力内建进引擎；
- 早期 AI 生成的需求文档——对意图理解有偏差，未作为设计依据保留；
- `MicaJIT-PY` 这一代号——没有 JIT，名不副实，后改为 Mica-PY。

## 怎么验证

AI 汇报"完成"不等于验证完成。这个项目实际用了五层验证：

1. **回归测试**。每个阶段把内联断言固化为持久测试套件，后续阶段不得破坏旧示例的精确输出。用例数随阶段增长：20 → 66 → 97 → 135 → 183 → 195 → 198。
2. **双视角对抗性审查**。第五阶段由作者独立排查 + 子 agent 独立排查，最后汇合结论。子 agent 的价值在于视角不同，不在于更聪明——它发现的快照放大、内存总账缺失都是作者自查漏掉的。
3. **外部独立意见**。另一 AI 的安全审查意见经三分类处理：可采纳的修复并附回归测试，牛角尖不采纳也不入档，合理但工程量过大的记入日志展望。
4. **文档盲测**。设计文档写完后，让未参与写作的子 agent 只读文档再复述理解；第一轮发现四处误导，修正后第二轮才通过。文档像代码一样需要测试。
5. **端到端实测**。CLI 示例精确输出断言、demo 的 mock 桩全链路、真实 API 多轮运行，以及作者本人复跑。`IfExp` 崩溃就是"AI 说全绿"与"用户实际使用"之间的差距的实例。

此外还有一条文档与实现互相校验的规则：速览文档曾教模型使用三元表达式，而引擎并不支持——问题既可能是代码缺功能，也可能是文档写错。这里判断三元表达式合理且无安全隐患，于是补进语言。因此，代码与文档的同步维护，在开发过程中值得特别关注。

## 边界

- AI 参与不等于质量已被证明。引擎仍是原型，安全边界以[安全模型](../security.zh-CN.md)为准。
- 本文不给出"AI 写了百分之多少"这类数字：按行数或比例衡量没有实际意义，分工方式如上所述。
- 本文自身也遵循同一规则：AI 起草，作者人工修改后定稿。
