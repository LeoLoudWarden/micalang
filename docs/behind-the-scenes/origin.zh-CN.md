# 原动力：Mica 之前

Mica 不是我“想写一门语言”就拍脑门写出来的。Mica 的语言概念源自于一个具体的问题：LLM 生成的代码，要敏捷、动态、灵活地执行，但不能信任。

这篇文章记录 Mica *立项之前*的探索过程。源自于与LLM的聊天记录，经过整理再加工；如需*立项之后*原型开发阶段的原始对话的摘录，请移步至[开发对话选编](conversation.zh-CN.md)。

## 起点：不可信的代码

Agent 时代的应用要面对一个尴尬的事实：让 LLM 干活，往往意味着执行它现场生成的代码。文件操作、文本处理、调 API——这些代码不是恶意写的，但你没法逐行审查，也没法证明它无害。

最直接的想法是给这些代码一个假的物理机：虚拟文件系统、虚拟网络、虚拟一切。我当时已经有一个虚拟文件系统的雏形，于是自然的问题是：**代码执行这一层，能不能也这样虚拟化？**

## 第一问：能不能完整接管 CPython 的 IO？

在 python 中执行代码，常见的隔离层次有：
1. 粗放治理，eval() 与 exec()，毫无安全性 → 需求方向上的反面典型
2. 利用 python 的图灵完备，在python中写一个受控的python虚拟机 → 性能损失巨大
3. 关注 python 的虚拟机本身（如CPython），隔离整个进程 → 似乎可行

最初的想法很朴素：在 Python 进程内部把 IO 全面接管：`open`、`sys.stdout`、`time`、网络库，让跑在里面的代码以为自己在跟真实世界打交道。

这个方向走不通，查证后发现：

- CPython 的 IO 层散布在对象层、C API、原生库、系统调用之间。以文件入口为例，除了`open()` ，还存在`os.open`、`os.stat`、`os.listdir`、`os.environ`、动态链接库、C 扩展…出入口零散且多，如同箩筐，不存在可以整体替换的接口。
- CPython 断不掉真OS信息链路。报错信息会泄漏真实路径，`sys.stdout` 接管不了所有输出，网络也不止 `requests` 一个入口。
- audit hook 能看到事件，但粒度太粗，做不了细致的治理。

结论很清楚：**在 Python 内部，造不出一块干净的隔离地。**

## 向外看一圈

内部造不出来，那就向外找。已有的方案大致分布在一条成本光谱上：

- **monkey patch / 库级拦截**：上面说了，堵不住。
- **独立子进程 + OS 隔离**：方向对，但进程这个单位太重。一个进程能发起的系统调用"菜单"极其复杂，内核没有足够证据判断每次调用是否在干坏事，所以 OS 管进程这件事本身漏洞频出。
- **容器 / microVM（gVisor、Firecracker）**：隔离强度够，但每执行一段代码要初始化一整套环境，磁盘、内存、启动延迟都摆在那里。面对"成百上千段生成脚本"的场景，太贵。
- **WASM / Pyodide**：隔离边界清晰，但生态割裂——代码不再是你熟悉的 Python，数据进出要跨边界序列化。
- **Starlark**：最接近的一个。语法接近 Python，默认无网络无文件系统，能力全靠宿主注入，已有多种实现。如果目标只是"让 LLM 做受限的文件和文本处理"，Starlark 完全可以作为第一版。

这里插一句历史的公平话：走到 Starlark 这一步时，最初的需求其实已经"满足"了。给 LLM 一个 Starlark 执行工具，配上虚拟文件系统和结构化错误，能用。

## 转折

但 Starlark 的答案暴露了一个更深的问题。

它的隔离边界是**外界施舍的**：宿主决定给它什么能力、什么文件视图、什么资源限制，而脚本自己没有"创建一块隔离地"的能力。我们可以把脚本A装到一个安全的盒子里，如果脚本A拿到一段新的不可信代码B要执行呢？不可信性在现实里是层层传递的。在盒子里的脚本A，怎么创建一个新的盒子运行自己觉得不可信的B？如果盒子本身不能提供给A这个能力，如果A需要一个新盒子来运行B，必须跳出A自己的盒子进行某些操作，隔离就退化为了一种有例外的习惯法。

另一个观察来自工程实践：跨语言协作（比如 Python 调 Go）时，数据大了要跨边界传输、复制、序列化，开销明显。如果一门语言内部就能完成状态共享与隔离——像多线程之于进程、协程之于线程那样——这一切就是语言内部的事。

于是问题被重新表述为：

> **能不能让"创建一个完全隔离的子虚拟机"成为语言的第一类能力？便宜到可以随手使用，可以任意嵌套，并且每一层都完全管理自己的 IO、资源和调试？**

这是能做到的吗？当时没有现成答案。已有的方案都不在这个点上：要么太重，要么边界由外界施舍，要么语言本身没把这件事当作第一类概念。

## 于是有了 Mica

Mica 就是为回答这个问题而生的：不接管 CPython，不套容器，不借 WASM，自己造一个小到可以验证的执行引擎，让 `VM(code)` 成为一句普通脚本语句。

从第一问到这个问题的转变，是本项目真正的起点。至于这个问题落实下来长什么样（语法、隔离、能力授予、资源配额）见[设计说明](../design.zh-CN.md)；一步步怎么造出来的，见[构建手记](../stages/README.zh-CN.md)。
